# Режимы Kilo Code: одна просьба, четыре результата

Чтобы прочувствовать разницу между режимами, я попросил Kilo одно и то же
четырьмя способами: **code**, **ask**, **plan** и **debug**. Просьба:

> «В README не хватает раздела "Как проверить, что сервис жив". Разберись по
> Makefile и docker-compose.yml, какие команды для этого есть, и добавь такой
> раздел в README.»

Ниже — что реально получилось в каждом режиме. Code-вариант — это то, что
агент сделал вживую (правки в `README.md`, файл `docs/setup/modes.md` создан
этой командой). Ask, plan и debug я воспроизвёл мысленно по правилам режимов
и своему опыту работы с Kilo: в них файлы не правились, проверяющий это легко
увидит по `git diff` ветки `d1/1.2.1-1.2.3-pilin-dev`.

## Что вообще делают режимы

| Режим | Что умеет | Чего не делает |
|---|---|---|
| **code** (по умолчанию) | читает файлы, правит, запускает команды, коммитит | не торгуется о плане — сразу делает |
| **ask** | читает, ищет, отвечает текстом со ссылками `file:line` | **не правит файлы и не запускает команды** |
| **plan** | то же, что code, но сначала показывает план и ждёт «ок» | не редактирует, пока не одобришь |
| **debug** | code + активный сбор диагностики: логи, healthcheck, трассировка запросов | подходит для живого сервиса; для правки документации — избыточен |

## code — то, что сделал я

Промпт был «добавь раздел в README», без оговорок. Kilo в режиме code:

1. Прочитал `Makefile`, `docker-compose.yml`, `README.md` параллельно
   (три `read` за один вызов — это видно по логу).
2. Сопоставил команды Makefile и порты compose, нашёл `make ps`, `make logs`,
   эндпоинт `/health` и `POST /api/ltv`.
3. Один `edit` в `README.md:33-67`: вставил раздел «Как проверить, что сервис
   жив» между таблицей команд и API, попутно добавил `make ps` и `make logs`
   в основную таблицу (раньше их там не было — нашёл через `make help`).

Раздел получился рабочий: три команды проверки (`make ps`, `curl /health`,
`curl POST /api/ltv`), замечание про `APP_PORT` для стенда и таблица
«симптом → что проверить → куда смотреть» с опорой на существующие
`make logs` / `make ps`.

Что я бы улучшил задним числом: `curl` без `-fsS` прячет ошибки в выводе
(как в моём варианте), а с `-fsS` фейл видно сразу — стоило сразу так писать.
В режиме code агент такие мелочи оптимизирует только если попросить.

## ask — что было бы, если бы я переключился

В режиме ask Kilo отвечает текстом и **файлы не трогает**. На ту же просьбу
ожидаемый результат — что-то вроде:

> В `Makefile` для проверки живости есть `make ps` (состояние контейнеров,
> `Makefile:24-25`) и `make logs` (стрим логов backend'а, `Makefile:27-28`).
> Эндпоинт `/health` уже описан в `README.md:38`. Compose поднимает backend
> на 8080 (`docker-compose.yml:14-15`) и MySQL с healthcheck
> (`docker-compose.yml:38-42`). Готовых команд «проверь что жив» нет —
> обычно это `make ps` + `curl http://localhost:8080/health`. Хочешь, я
> переключусь в code и добавлю раздел?

Проверяющий увидит по `git status`: ни одного изменения, только файл
`modes.md`. Это и есть главное отличие ask от code: **спросили — ответили,
ничего не тронули**. Удобно, когда хочется сначала понять, что вообще есть,
и только потом просить правки.

## plan — что было бы с планом

В режиме plan агент сначала показывает план и спрашивает одобрения. На той же
просьбе он бы, скорее всего, написал что-то вроде:

> **План:** вставлю в `README.md` раздел «Как проверить, что сервис жив»
> между таблицей команд и разделом API. Внутри — три проверки
> (`make ps`, `curl /health`, `curl POST /api/ltv`), заметка про `APP_PORT`
> и мини-таблица «если что-то не так». Заодно добавлю `make ps` и `make logs`
> в основную таблицу команд — сейчас их там нет. Файлов больше не трогаю.
> Начинать?

Я бы сказал «ок» — и дальше всё пошло бы как в code, только с лишним шагом.
Plan полезен, когда задача нетривиальная (правки в нескольких местах, надо
заранее согласовать структуру) или когда тронешь чужие файлы. Для одного
`edit` в README это скорее overhead, чем польза.

## debug — что было бы в режиме отладки

Режим debug — это code плюс активный сбор диагностики: логи, healthcheck,
трассировка HTTP-запросов. Для правки документации он **избыточен**:
документация не падает и не возвращает 500, ей не нужен `docker compose logs`
и `curl -v`.

Если бы я случайно попросил это в debug, агент, вероятнее всего:

1. Поднял бы сервис (`make up` или проверил, что уже поднят).
2. Простучал бы `curl -v http://localhost:8080/health` и
   `curl -v -X POST .../api/ltv`, вытащил бы реальные тела ответов.
3. Убедился бы, что `make ps` показывает `healthy` у `db` (через
   `mysqladmin ping`, см. `docker-compose.yml:38-42`).
4. И только после этого написал бы раздел — причём с фактическими ответами
   API, а не с моим ожидаемым `{"status":"ok"}`.

Для живой системы это плюс: раздел сразу с настоящими примерами ответов.
Для пустого README на учебном проекте — лишние минуты на подъём контейнеров.
В нашем случае вышло бы то же самое, только дольше.

## Что я вынес из этого упражнения

- **code** — рабочая лошадка: сказал — сделал. По умолчанию.
- **ask** — когда хочется сначала картину мира, а потом решать. Файлы чистые.
- **plan** — когда правка затрагивает чужой код или несколько файлов и хочется
  заранее увидеть, что именно собирается менять.
- **debug** — когда сервис живой и надо чинить, а не писать документацию.

Главный практический вывод: режим — это не настроение, а **договорённость о
том, можно ли трогать файлы**. Если перепутать code и plan, получишь правки
без спроса; если перепутать code и ask — пустой ответ там, где ждал diff.
